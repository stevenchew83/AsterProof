# Catalogue backup and maintenance release

The human request to create an AsterProof production database backup, verify an isolated restore, and proceed with the catalogue migration/deployment authorizes this scoped procedure. The earlier bounded deployment-helper authorization remains applicable. Resolve the exact merged main SHA and attested archive before installation or submission. This document does not grant unrelated authority.

## Scope and preflight

Use only the configured `asterproof-prod` administration alias and existing protected Actions deployment path. Preserve the current application, existing credentials/roles, target contract, service configuration, network and IAM controls. Do not install or replace system PostgreSQL packages.

The verified source is PostgreSQL 17.9, UTF8, libc locale `en_US.UTF-8`, with only `plpgsql` installed. Source size was approximately 478 MB. The host has 16.15 client tools and about 412 MB RAM. The pinned PostgreSQL 17.9 runtime is therefore packaged as regular files with private libraries/locale data, included in the attested release archive, and installed separately through the authorized host-administration step. Verify archive provenance, exact SHA, manifest/digests, root ownership and read-only modes first. Native programs execute under existing unprivileged accounts.

Before stopping traffic, verify the current release/process/health/schema identity, complete exact pending plan, installed helper/runtime source revision and hashes, free-space reserve, source scope, and loaded paired scheduler timer. The source audit connection and application backup connection must identify the same database/server tuple; their role-dependent identity hashes are normalized explicitly. Unknown clients after drain are a failure, never a reason to terminate arbitrary sessions.

## Single protected operation

1. Build and attest the exact current-main release, including passing PostgreSQL migration/compatibility proof and `deployment-postgres-runtime.tar`. Complete local/CI checks and the runtime/crypto/full-restore rehearsal before production installation.
2. Install only the frozen reviewed authority generation and matching private runtime through the established bootstrap procedure. Compare protected configuration/key bytes, modes and owners before/after. Preserve current/previous releases and the running app.
3. Derive the frozen catalogue disclosure from fresh catalog metadata and the hash-bound table delta. Bind the exact 0037–0039/seed hashes, starting/ending schema/migration/function/trigger fingerprints, packaged proof and fixed RPO0/encryption/isolation policy to the existing OIDC operation envelope. Inspect and approve its protected environment gate under the existing human deployment request.
4. The durable worker records `draining` before stopping the paired timer, scheduler service and request-serving app. Verify empty cgroups and absence of other database client writers. No persistent service/timer disable is introduced.
5. Record `backing_up`. Create one exclusive backup directory/key for this run ID. Keep a read-only repeatable-read source transaction open, export its snapshot, hash every user table/sequence/large object in bounded streams, and run matching `pg_dump --snapshot` against it. Encrypt the stream with a fresh AES-256-GCM key. No dump bytes or credentials are printed or transferred to the workstation/CI.
6. Authenticate and decrypt into the owned disposable restore directory. In a transient service using the existing audit OS account, run a separate PostgreSQL 17.9 cluster with a private Unix socket, `PrivateNetwork`, no production environment, fixed writable scratch path, constrained memory and no parallel workers. Restore the whole archive and compare all data and schema digests. The recovery-only schema comparison removes dropped-column physical slot gaps and canonicalizes only two exact existing PostgreSQL 17 literal-array cast rewrites; source catalogue auditing retains its original strict fingerprint. Root retains only metadata, ciphertext and key after successful verification; stop the cluster and delete only its owned scratch directory.
7. Recheck the root-private receipt, key/archive/manifest digests, target/release/run binding, timestamps and 30-minute freshness. Re-audit schema/trigger state and writer absence. Only then enter `migrating` and execute the exact frozen plan through `MigrationExecutor`, with bounded locks/statements and no unrelated post-migrate writes.
8. Publish the initial derived catalogue summary. Verify expected schema/function/trigger fingerprints and compare original user, completion, problem UUID, statement, assignment, tag and study-note records against the backup digests. Activate and verify the immutable application/static release, then resume the timer if it was active before the operation.

## Recovery artifacts and limitations

Root-only ciphertext, manifest and receipt are under `<release-root>/registry/recovery/<run-id>/`; the root-only key is in the separate `<release-root>/registry/recovery-keys/<run-id>.key`. These are outside replaceable candidate/release directories and unavailable to app, build and deploy identities. The fixed restore scratch directory is outside those backup directories. Keep the encrypted recovery point and key after release; no automatic retention deletion is part of this operation.

This is a same-host, database-only operational recovery point. It does not protect against loss of the host/storage and does not back up media or external secrets. Source Amazon libc collation version and local rehearsal collation version differ; record both truthfully. Data comparisons use deterministic C ordering, and restoration rebuilds indexes/constraints, but this does not certify a platform upgrade or permission to restore over production.

Any interruption/failure after draining is `recovery_required`. Preserve the original run ID, backup files and private diagnostics; reconcile before another submission. Never blindly repeat, migrate backward, restore over production, switch code automatically, or silently resume traffic after a failed migration. Ordinary rollback from the active data-class release is blocked. A production restore or code recovery requires its own exact reviewed operation; a successful isolated restore does not authorize it.
